# Roadmap — protocol gap remediation, 2026-11-23

Source of findings: the gap analysis earlier in this session (full text in
git history of this file) plus `ROADMAP-2026-11-22.md`. This document is the
execution plan: milestones are ordered, each has acceptance criteria, and the
status line is updated as work lands.

**Targets:** current stable v1.19 conformance gaps first, then the v1.20
release train on spec `main` (delayed events, sticky events, query-string
tokens, `prev_sender`).

**HITL flags:**
- **M6** touches `src/middleware/auth.ts` — flagged for human review before
  merge per AGENTS.md.
- **M8** adds a migration (`migrations/023_…`) — flagged for human review
  before merge per AGENTS.md; no existing migration is modified.

**Explicit non-goals (role decisions, documented not coded):**
- Identity Service v2 completion (14 endpoints). This Worker does not
  advertise `m.identity_server` in `.well-known/matrix/client`; completing it
  is a product decision.
- Appservice *receiver* endpoints (`/app/v1/transactions`, thirdparty
  query form). Outbound fanout already works; the receiver surface is a test
  harness, not homeserver behaviour.
- Push Gateway `/_matrix/push/v1/notify` — this is a homeserver, not a
  gateway.

## M1 — Delayed events stabilization (MSC4140, spec v1.20)

**Spec:** `content/client-server-api/modules/delayed_events.md`,
`data/api/client-server/delayed_events.yaml` on `matrix-spec` `main`.

**Changes**
1. `src/api/delayed-events.ts` — register the stabilized routes in addition to
   the unstable ones:
   - `PUT /_matrix/client/v3/rooms/{roomId}/delayed_event/{eventType}/{txnId}`
   - `GET /_matrix/client/v1/delayed_events/{delayId}`
   - `POST /_matrix/client/v1/delayed_events/{delayId}/{send|cancel|restart}`
2. `src/index.ts` — advertise **`m.delayed_events`** (`max_delay_ms`,
   `max_scheduled`); keep the unstable key for older clients.
3. `src/services/delayed-events.ts` — dispatch passes the delay id to the send
   core and stops passing the scheduling `txn_id`; on success the resulting
   event carries `unsigned.delay_id`.
4. `src/api/rooms.ts` — `performSendEvent` / `performStateEvent` accept an
   optional `delayId` and place it in `unsigned`; serve paths strip
   `unsigned.delay_id` unless the viewer is the event's sender.

**Acceptance**
- Stable paths return the same bodies as the unstable ones; capability has the
  spec key; a GET on the sent event shows `unsigned.delay_id` to the sender
  and not to another member; no `unsigned.transaction_id` on dispatched events.
- Targeted tests + `npm run typecheck`.

**Risk:** low. No schema change (linkage already exists via
`delayed_events.final_event_id`).

## M2 — `unsigned.prev_sender` (spec v1.20, #2427)

**Spec:** "The user ID of the sender of the previous state event that was
replaced by this event… only returned if the event is a state event. Unlike
`prev_content`, included regardless of history visibility."

**Changes**
- `src/services/replaces-state.ts` — extend the existing predecessor CTE to
  select `prev.sender`; attach `unsigned.prev_sender` beside
  `unsigned.replaces_state` for state events. No schema change.

**Acceptance**
- A state event served over `/state`, `/sync`, `/context`, `/messages` carries
  `unsigned.prev_sender` for the replaced state event, even when history
  visibility hides `prev_content`.

## M3 — Push-rule GET endpoints

**Spec:** `GET /_matrix/client/v3/pushrules/global/{kind}/{ruleId}/actions`
and `.../enabled` are required; only the PUT forms exist today
(`src/api/push.ts:843`, `:901`).

**Changes**
- `src/api/push.ts` — two GET handlers resolving the rule through
  `getUserPushRules` (same lookup as the existing GET-rule handler) and
  returning `{actions}` / `{enabled}`; `M_NOT_FOUND` for unknown rules,
  `M_INVALID_PARAM` for unknown kinds/scope.

**Acceptance**
- GET mirrors the stored state set by PUT for custom and default rules,
  including enabled overrides of default rules.

## M5 — Federation `3pid/onbind`

**Spec:** `POST /_matrix/federation/v1/3pid/onbind` (verb fixed from PUT in
v1.20). Body `{medium, address, mxid, invites[]}`; returns `{}`.

**Changes**
- `src/api/federation.ts` — new signed-request endpoint: bind the 3PID to the
  local `mxid`, then for each pending invite verify the identity-server
  signature (reuse the signature helpers used by
  `exchange_third_party_invite`, `:5029`) and issue the `m.room.member`
  invite; skip/record invalid entries without failing the whole request.
- Reuse `m.room.third_party_invite` state stored by
  `src/api/rooms.ts:2639-2690` where available.

**Acceptance**
- 200 `{}` on a valid payload; unsigned invites are not honoured; a row for
  the bound 3PID exists so `/account/3pid` and invites reflect it.

**Risk:** medium — signature/identity-server semantics; keep the handler
defensive and log-and-skip per invite.

## M6 — Query-string access tokens removed (HITL, breaking in v1.20)

**Spec:** "Sending the access token as a query string parameter is no longer
supported." (`changelogs/client_server/newsfragments/2408.breaking`)

**Changes**
- `src/middleware/auth.ts` — remove the `access_token` query fallback; a
  request without an `Authorization: Bearer` header is unauthenticated
  (`M_MISSING_TOKEN`), and a query token no longer authenticates.
- `CLAUDE.md` / docs — drop the "or `?access_token=`" statement; add a note to
  `ROADMAP-2026-11-23.md` status.
- Tests — update `test/auth-middleware-*.test.ts` expectations for query
  tokens; keep asserting no-auth behaviour for missing/invalid headers.

**Acceptance**
- Full suite green after the test updates; grep shows no remaining
  `searchParams.get('access_token')` in `src/`.

**HITL:** yes — auth middleware. Do not merge without review.

## M8 — Sticky events as real PDUs (MSC4354, spec v1.20; HITL migration)

Current implementation (`src/api/account-data.ts:94-260`) stores sticky events
as `account_data` rows with fabricated IDs, no timeline, no federation, and
client-supplied `event_id`/`origin_server_ts`. Spec wants real message PDUs
with a top-level `sticky` member in every room version, `sticky_duration_ms`
on `/send` and the delayed-event body, `unsigned.sticky_duration_remaining_ms`,
and the `sticky.events` `/sync` section for unexpired events outside the
timeline limit.

**Changes**
1. `migrations/032_event_sticky.sql` (new file; next free number after 031 — never modify existing files):
   `ALTER TABLE events ADD COLUMN sticky TEXT;` and
   `ALTER TABLE events ADD COLUMN received_ts INTEGER;` (+ optional index).
2. `src/types/matrix.ts` — `sticky?: { duration_ms: number }` on PDU.
3. `src/services/database.ts` — persist `sticky` and `received_ts` in
   `storeEvent` / `storeEventIdempotent`; return them from the row→PDU
   mappers used by the serve paths.
4. `src/api/rooms.ts` — accept `sticky_duration_ms` on
   `PUT /rooms/{roomId}/send/{eventType}/{txnId}` (query param, positive
   integer, clamp at send time per spec), stamp `sticky` on the PDU before
   hashing; empty/0 → `M_INVALID_PARAM`. Delayed-event PUT accepts the
   `sticky_duration_ms` body property.
5. Serve path — shared enrichment helper (extend
   `src/services/replaces-state.ts` or a new
   `src/services/served-event-metadata.ts`) attaches top-level `sticky` and
   `unsigned.sticky_duration_remaining_ms` (start =
   `min(received_ts, origin_server_ts)`, capped at 1 h, omitted when expired);
   applied where `attachReplacesState` is already applied plus `/messages`.
   Redacted events lose `sticky` (not protected from redaction).
6. `src/api/sync.ts` — build `sticky.events` from unexpired sticky PDUs
   outside the applied timeline limit (dedupe against timeline, cap 100,
   ignore `state`/`timeline` filters for the sticky section); keep serving
   legacy account-data sticky rows under the unstable prefix for
   backwards compatibility.
7. Federation — `sticky` travels in outbound wire events
   (`src/services/event-wire.ts`) and is preserved on ingest (validator +
   `storeEvent`); redaction strips it.
8. `src/api/account-data.ts` — keep the unstable endpoints as a legacy shim
   (documented), or mark deprecated in comments.

**Acceptance**
- Send with `sticky_duration_ms` produces a real timeline event, visible in
  `/messages`, `/event`, `/state`? (no — message event), `/sync` timeline and
  `sticky.events` only when outside the timeline limit; `sticky` survives a
  federation round-trip in tests; redaction removes it; expired events lose
  `unsigned.sticky_duration_remaining_ms`.
- Existing sticky tests either keep passing against the legacy shim or are
  updated to the PDU semantics with a clear rationale.

**HITL:** migration. Do not merge without review.

What landed per milestone:

  addition to the unstable aliases; `/capabilities` advertises
  `m.delayed_events` (unstable key kept); `src/services/served-events.ts`

  alongside `replaces_state` from one batched predecessor query.
- **M3** — `GET .../pushrules/{scope}/{kind}/{ruleId}/actions` and `/enabled`
  added in `src/api/push.ts`.
- **M4** — `POST /_matrix/media/v1/create` and
  `PUT /_matrix/media/v3/upload/{serverName}/{mediaId}` serve the existing
  handlers; the non-spec `/client/v1` aliases remain.
- **M5** — `POST /_matrix/federation/v1/3pid/onbind` implemented and exempted
  from X-Matrix auth (identity servers cannot sign it); signatures verified
  against `m.room.third_party_invite` state via the new

- **M6** — `src/middleware/auth.ts` accepts only `Authorization: Bearer`;

  replaced with a header-only suite plus explicit "query is not a credential"
  coverage).
- **M7** — `m.policy` room type pinned by a createRoom conformance test; docs
  updated.
- **M8** — migration `032_event_sticky.sql` (`events.sticky`,
  `events.received_ts`, `delayed_events.sticky_duration_ms`); `sticky` is part
  of the PDU, stored through both event stores, carried in derived federation
  wire events; `/send` and delayed send accept `sticky_duration_ms`; served
  events gain top-level `sticky` + `unsigned.sticky_duration_remaining_ms`
  (redacted events suppressed); `/sync` merges unexpired sticky PDUs into
  `sticky.events`.
- **M9** — docs/README/CLAUDE.md updated; full suite green.

**HITL items — do not merge without review:**
1. `src/middleware/auth.ts` (+ `src/api/devices.ts`): query-string token
   rejection. This is a breaking change for clients still passing
   `?access_token=`; coordinate the rollout.
2. `migrations/032_event_sticky.sql`: additive schema change (three columns,
   no data transform). Existing rows keep NULL and read as non-sticky.

**Known deviations / follow-ups:**
- `/sync` re-delivers unexpired sticky PDUs until they expire rather than
  tracking a per-user sticky stream cursor (the spec's once-only delivery).
  Clients are required to tolerate duplicates and de-duplicate by event ID;
  the alternative (a per-user cursor table) was judged out of scope here.
- The legacy account-data sticky endpoints
  (`/_matrix/client/unstable/{msc4354,msc4480}/...`) are retained for older
  clients; they are not part of the stable spec and do not federate.
- Sticky events are not yet included in the sliding-sync (`MSC4186`) response
  builder; classic `/sync` is covered.
- `3pid/onbind` forwards remote-room invites to the room ID's domain; rooms
  whose invite-issuing server differs from the room domain rely on that
  server accepting the exchange.
