# Spec v1.19 audit roadmap — 2026-11-22 session

Suggested actions derived from an audit of this codebase against the
[Matrix Specification v1.19](https://spec.matrix.org/v1.19/) (changelogs for
v1.17 / v1.18 / v1.19 reviewed, plus targeted reads of the spec text for
`/capabilities`, federation `/state`, `/state_ids`, and `query/profile`).

Audit method: full registered-route sweep (~250 `/_matrix/*` routes), then
spec-by-spec cross-check of every v1.17→v1.19 stabilization, with file:line
verification in `src/`. A second read-only subagent verification round
(8 hy4-flash agents) then confirmed or refuted the open questions, and every
merged claim below was spot-checked against the code. No code was changed
this session — this file is the deliverable.

---

## P0 — Spec conformance gaps (small fixes, client-visible)

### 1. Serve `timestamp_to_event` on the spec's `v1` path
- **Spec:** `GET /_matrix/client/v1/rooms/{roomId}/timestamp_to_event`
  (verified against the v1.19 C-S spec text). The spec also suggests falling
  back to the federation endpoint when local history can't satisfy the ts.
- **Code (verified):** only `/_matrix/client/v3/rooms/:roomId/timestamp_to_event`
  is registered (`src/api/rooms.ts:3939`) — an inline anonymous handler, so
  this is NOT a one-line alias: extract a named handler first (pattern
  exists: `getRoomStateHandler` is named and registered twice,
  `rooms.ts:1341`, `:1349-1350`). Success shape is spec-correct
  (`{event_id, origin_server_ts}`, `:4003-4006`); non-members get a 403
  (`:3971-3974`); no matching history → 404 (`:3999-4001`). There is NO
  federation fallback — the handler queries local `events` only
  (`:3979-3997`). The federation twin is correctly on v1
  (`src/api/federation.ts:4871`).
- **Fix:** extract `timestampToEventHandler`, register v1 + v3. Optionally
  add the federation fallback the spec suggests when local history can't
  satisfy `ts`.
- **Tests:** v1 path 200 (mirror `test/rooms-api-routes.test.ts:3120`); 404
  on unknown room; validation errors.

### 2. `make_join` / `make_knock` `ver` negotiation
- **Spec:** both endpoints take a repeated `?ver=` list of room versions the
  caller supports; if none matches the room's version, the server MUST
  respond `400 M_INCOMPATIBLE_ROOM_VERSION` with its supported
  `room_versions` in the error body.
- **Code (verified):** `ver` is ignored everywhere (no `query('ver')` in
  `src/api/federation.ts`); the template is returned unconditionally with
  `room_version` (`federation.ts:2553-2556`). Without this, a version-limited
  peer only discovers the mismatch after building and signing a join event.
  Our own outbound joiner already sends `ver` params
  (`src/workflows/RoomJoinWorkflow.ts:571-573`) — resident servers that
  ignore them are what we experience here from the other side.
- **Fix:** after the room lookup in `make_join` (`federation.ts:2401-2407`)
  and `make_knock` (`federation.ts:4090-4096`), read the repeated param via
  Hono's `c.req.queries('ver')`; if non-empty and the room's version is not
  in it, return `400 M_INCOMPATIBLE_ROOM_VERSION` with a `room_versions`
  map reusing `SUPPORTED_ROOM_VERSIONS` (`federation.ts:135`) or the
  `/capabilities` map (`src/index.ts:186-202`).
- **Also fix:** the existing `M_INCOMPATIBLE_ROOM_VERSION` response in the
  invite path (`federation.ts:3533-3536`) omits the spec-required
  `room_versions` map — add it.
- **Tests:** `ver` without the room's version → 400 + `room_versions` map;
  `ver` including it → 200 template; no `ver` → current behavior preserved;
  repeated `ver` params handled.

### 3. `unsigned.replaces_state` on *served* events (half-implemented)
- **Spec (v1.19, #2345/#2403):** client-formatted state events carry
  `unsigned.replaces_state`.
- **Code (verified):** the value IS attached before storage on locally-PUT
  state events (`src/api/rooms.ts:1448-1455`, persisted with the event's
  `unsigned`), so surfaces forwarding stored `unsigned` already show it —
  /sync timeline (`sync.ts:834`), /messages (`rooms.ts:1768`), /event
  (`rooms.ts:1818`). Remaining gaps: serializers that never build `unsigned`
  — GET /state (`rooms.ts:1306-1314`), sync full-state (`sync.ts:886`),
  `state_after` (`sync.ts:987`), leave timeline (`sync.ts:1144`), /context
  (`rooms.ts:3451-3472`) — and federation-origin state events, which never
  get a value at all.
- **Fix:** one shared helper injecting `unsigned.replaces_state` for state
  events on every full-event surface; for federation-origin events compute
  it at serve time from the previous state event for that (type, state_key),
  bounded to the returned window (perf: one lookup per state event).
- **Tests:** overwrite a state key; every read surface reports
  `replaces_state` = previous event's ID, for both a local PUT and a
  federated state event.

### 3a. `/context` ignores the `filter` parameter
- **Spec:** `GET /rooms/{roomId}/context/{eventId}` supports a `filter`
  (event-type/sender patterns, like /messages).
- **Code (verified):** only `limit`/`before`/`after` are parsed
  (`src/api/rooms.ts:3378-3380`); `filter` is silently ignored. `/messages`
  by contrast is conformant — `applyMessageEventFilter` applies
  types/not_types/rooms/not_rooms/senders/not_senders/contains_url
  (`rooms.ts:1661-1675`) and `to` is enforced as an exclusive stream bound
  (`:1719-1757`).
- **Fix:** run `applyMessageEventFilter` over `events_before`/`events_after`
  in /context. **Tests:** `filter={"types":["m.room.message"]}` excludes
  other types from both sides.

### 4. Federation `query/profile` `field` semantics (v1.19 clarification #2326)
- **Spec (verified text):** `field` MUST restrict the response to that field;
  defined values are `displayname`, `avatar_url` **and `m.tz`**, plus
  server-defined extra fields; a 404 is required when the queried field does
  not exist; unset fields MUST be omitted or `null`.
- **Code (`federation.ts:3706`):** handles `displayname`/`avatar_url`, but
  any other `field` silently falls through to the full profile (spec says
  404), and the full-profile query selects only `users.display_name` /
  `avatar_url` — custom profile keys are never exposed to federation.
  **Verified storage:** custom fields live in the CACHE KV under
  `profile:${userId}:custom` as a JSON object (`src/api/profile.ts:212`,
  read/written at `:250`, `:289`, `:297`, `:322`, `:330`); `m.tz` has zero
  matches in `src/` — it is just an ordinary custom key.
- **Fix:** in the federation handler, read
  `CACHE.get(profile:${userId}:custom)` and honor arbitrary `field` keys;
  return the full public profile (including public custom fields) when
  `field` is absent; 404 for nonexistent fields.
- **Tests:** `field=m.tz` returns only `m.tz`; unknown field → 404; no field
  → displayname + avatar_url + public custom keys.

### 5. Identity `submitToken` must return `M_TOKEN_INCORRECT` (MSC4183, v1.18)
- **Spec:** Identity Service `POST /_matrix/identity/v2/validate/email/submitToken`
  (and msisdn) returns `400 M_TOKEN_INCORRECT` for a wrong/expired token; the
  C-S `requestToken` flows share those error codes via `submit_url`.
- **Code (`src/api/identity.ts:174-205`):** returns `M_INVALID_PARAM`,
  `M_NO_VALID_SESSION`, `M_SESSION_EXPIRED` — none are the spec'd code.
- **Verified:** no `submit_url` is returned by any requestToken flow (zero
  matches in `src/`; responses carry only `{sid}` — `account.ts:411-413`,
  `identity.ts:170`). Both C-S submit_token variants validate against the
  same `email_verification_sessions` table as the identity endpoint
  (`src/services/email.ts:188-227`), so parity is already structural — but
  the C-S wrong-token error is `M_THREEPID_AUTH_FAILED` (`account.ts:462`,
  `:494`), also non-spec.
- **Fix:** wrong/expired token → `400 M_TOKEN_INCORRECT` on BOTH the
  identity and C-S submit_token handlers; optionally include `submit_url`
  in requestToken responses when an identity endpoint is configured
  (MSC4183).
- **Tests:** wrong token → `M_TOKEN_INCORRECT` on both sides; happy path
  unchanged.

### 5a. Federation `/send` per-PDU error objects (spec shape)
- **Spec:** the 200 `pdus` map's error values are Matrix error objects
  (`{"errcode": ..., "error": ...}`).
- **Code (verified):** the handler builds the spec-shaped map
  (`pduResults[eventId]`, `federation.ts:867`) but every error value is a
  bare string — e.g. `{ error: 'Invalid sender format' }` (`federation.ts:944`,
  also `:963`, `:985`, `:999`, `:1039`, `:1073`). The 503-on-transient
  posture from 6c00b4e is correct and interacts cleanly (no txn-idempotency
  row, processed_pdus written only post-storage).
- **Fix:** wrap per-PDU errors as Matrix error objects; ~50 existing tests
  assert the string form and must be updated in the same change.
- **Tests:** a representative per-PDU failure returns an errcode object;
  the 503 transient path still skips the txn cache.

### 5b. Federation `/backfill` + `/get_missing_events` parameter validation
- **Spec:** `/backfill` requires `v` and `limit`; unknown `v` → 404
  M_NOT_FOUND. `/get_missing_events` defaults `limit` to 10 with a max of 10
  and requires `earliest_events`/`latest_events`.
- **Code (verified):** `/backfill` makes both params optional (default 100,
  cap 1000 — `federation.ts:2002-2003`); a missing `v` serves "most recent
  events", and an unknown `v` yields an empty 200 (maxDepth 0 → no rows,
  `federation.ts:2037-2048`) instead of 404. `/get_missing_events` caps
  `limit` at 100, not 10 (`federation.ts:2109`), and treats both event
  arrays as optional (`:2106-2107`).
- **Fix:** 400 M_MISSING_PARAM for missing `v`; per-ID existence check →
  404 M_NOT_FOUND for unknown `v`; clamp get_missing_events to
  `Math.min(body.limit ?? 10, 10)`; require both arrays. Consider lowering
  the backfill cap from 1000 toward ~100 to bound response size.
- **Tests:** missing `v` → 400; unknown `v` → 404; `limit=50` on
  get_missing_events returns ≤ 10 events.

### 5c. Media route hardening: `mxc://` sanitization + PUT upload size cap
- **Spec (security section, MUST):** sanitize `mxc://` URIs — restrict the
  `server-name` segment to valid server names and the `media-id` segment to
  `[A-Za-z0-9_-]`.
- **Code (verified):** download/thumbnail routes take `serverName`/`mediaId`
  path params with NO validation at all (`src/api/media.ts:471-473`,
  `:542`); arbitrary strings flow into R2 keys and D1 binds. Outbound
  federation is mitigated (`mediaId` is `encodeURIComponent`'d, `:337`) but
  `serverName` is unvalidated.
- **Also (verified):** the MSC3916 PUT upload route skips both the MIME
  whitelist and the 50 MiB size cap that POST /upload enforces
  (`media.ts:807-845` vs `:184-218`) — an authenticated user can store
  unbounded content through the placeholder flow.
- **Fix:** shared server-name/media-id validators + 400 M_INVALID_PARAM on
  all media routes; enforce MAX_UPLOAD_SIZE (Content-Length + actual body)
  on the PUT route. **Tests:** traversal-shaped `mxc://host/../...`
  rejected; oversized PUT → 413.

### 9. Encrypted history sharing (MSC4268, v1.19)
- **Verified (subagent round): all relay obligations are already met.** The
  to-device PUT never type-checks (the URL param is bound verbatim,
  `src/api/to-device.ts:319-424`), the outbound `m.direct_to_device` EDU
  relays content wholesale (`to-device.ts:417-426`;
  `FederationDurableObject.ts:282-301`), inbound accepts any string type
  (`to-device.ts:253`), `/keys/query` has no membership gate — invitees
  query fine (`keys.ts:351`; the `join` gate at `:693` belongs to
  `/keys/changes`) — and federation `user/keys/query` checks only
  federation auth + user locality (`federation.ts:3774`, `:3824-3836`).
- **Action:** tests only — an `m.room_key_bundle` + `shared_history` relay
  test through `/sync` and the federated EDU; an invited-user device-key
  query test; probe whether clients still read an
  `org.matrix.msc4268` unstable flag on `/versions`.

### 10. Room directory ordering (MSC4423, v1.19)
- The spec now permits server-defined ordering (was largest-first). Current
  `listPublicRooms` order is incidental rather than pinned.
- **Action:** make the order intentional (recent-activity ranking is the
  useful choice for a directory), pin it in tests, and note it in README.

### 10a. Guest join enforcement (new finding)
- **Spec:** guests may only join rooms whose `m.room.guest_access` state
  permits them; servers reject with 403 `M_GUEST_ACCESS_FORBIDDEN`.
- **Code (verified):** `kind=guest` registration works (opaque localpart,
  `users.is_guest` set, registration-token gating applies — `login.ts:458-465`,
  `database.ts:42-44`), but NO join path checks it: `guest_access` is read
  only for metadata (`rooms.ts:382`, `:3894-3901`, `federation.ts:4725-4726`),
  neither C-S join handler checks `is_guest` (`rooms.ts:848`, `:3537`),
  federation `make_join` gates only join rule/ACL (`federation.ts:2440-2476`),
  and `M_GUEST_ACCESS_FORBIDDEN` is defined but never used
  (`src/utils/errors.ts:108-109`).
- **Fix:** in both C-S join paths and `make_join`, load `users.is_guest` +
  the room's `m.room.guest_access` and reject with
  `M_GUEST_ACCESS_FORBIDDEN` when the room forbids guests.
- **Tests:** guest blocked from a `guest_access=forbidden` room; allowed
  into a `can_join` room; non-guests unaffected.

### 10b. `/sync` `include_leave` + explicit `timeline.limit` windowing
- **Code (verified):** `include_leave` is declared but deliberately ignored —
  left rooms are always emitted, with an in-code rationale (a room left on
  another device otherwise lingers in open sessions, `sync.ts:1124-1126`).
  Decide: keep as a documented deviation (note it in README) or honor the
  flag on initial sync only.
- **Suspect (verify before fixing):** `room.timeline.limit` is applied
  twice (`sync.ts:153-156` and the initial-window slice at `sync.ts:928-934`);
  an explicit limit may select the OLDEST N events — the same class of bug
  as the initial-sync window fixed in 0296e75 (which made the default
  window fetch newest-first). Audit the interaction; if confirmed, the
  filter application must slice the newest N, descending first.
- **Tests:** explicit `timeline.limit=5` returns the 5 newest events, not
  the 5 oldest; left-room emission behavior pinned either way.

## P2 — Appservice API completion (v1.17; optional while no external appservices)

### 11. MSC4326 device masquerade
- **Verified:** user masquerade via `as_token` + `?user_id=` works with
  namespace validation, but the masqueraded device is hard-coded
  `deviceId: null` (`src/middleware/auth.ts:117-121`); `device_id` is never
  parsed (`:87`).
- **Downstream that would respect a masqueraded device:** `/sync` gates its
  device block on `deviceId` (to-device fetch + OTK scoping, `sync.ts:624`,
  `:708-713`); per-device delivery filtering in `getToDeviceMessages`
  (`src/api/to-device.ts:450`, binds `recipient_device_id`, `:479`, `:500`).
- **Fix:** parse `?device_id=`, validate it belongs to the masqueraded
  user, set `auth.deviceId`. **Test:** as_token + user_id + device_id sync
  returns that device's to-device events.

### 12. MSC4190 appservice use of standard endpoints
- **Verified:** `POST /register` has NO appservice branch — registration
  always demands UIA (`m.login.dummy`/token) + password
  (`src/api/login.ts:443-590`; zero as_token references in the file).
  Device GET/PUT work under masquerade (`requireAuth` resolves the
  masqueraded user), but DELETE + `delete_devices` require a UIA password
  (`src/api/devices.ts:118-140`, `:175-198`) which an appservice cannot
  supply.
- **Fix:** add an as_token/`user_id` branch to register that creates the
  user directly (namespace-checked, no UIA); skip UIA on device deletion
  for appservice-authenticated callers. **Tests:** register-with-as_token
  creates the user; an appservice can delete a masqueraded user's device.

## P3 — Compatibility decisions and hygiene

### 13. Federation v1 `send_join` / `send_leave` (removed by MSC4376 in v1.18)
- Inbound v1 routes still served (`federation.ts:2626`, `3225`); outbound is
  already v2-only (`src/workflows/RoomJoinWorkflow.ts:737`). The routes carry
  a comment documenting the MSC4376 removal decision (`federation.ts:3220`).
- **Verified shapes (keep-as-compat is safe):** v1 `send_join` already
  returns the full v2-shaped envelope — `{origin, auth_chain, state, event}`
  (`federation.ts:2711-2717`, legacy branch `:2765-2782`) — a superset of the
  2019-era `{state, auth_chain}` shape, which lenient peers ignore; v1
  `send_leave` returns `{}` (`federation.ts:3215-3217`).
- **Remaining action:** keep + document in the README spec table, and pin
  both shapes in tests (v1/v2 `send_join` include `origin`/`event`/`state`/
  `auth_chain`; v2 adds `servers_in_room`; v1 `send_leave` returns `{}`).
  No env gate needed.

### 14. Animated media + thumbnail/config validation
- **Verified:** `animated` is accepted-and-ignored on thumbnails (unknown
  params are ignored by Hono — permitted, since the spec only SHOULDs
  animation support). `width`/`height` are silently clamped (missing or
  garbage → 96, oversized → 1920; `media.ts:65`, applied at `:542-549`) and
  an unknown `method` silently becomes `scale` (`:67`) — decide whether to
  400 on invalid input; clamping is common server behavior.
- **Correction (do not "fix" backwards):** the media config field is
  `m.upload.size` (dot form) and that MATCHES the v1.19 spec text —
  verified in the spec and at `media.ts:731` (v1 route `:1077-1080`); it is
  NOT `m.upload_size`. Minor real gap: the v3 config route lacks
  `requireAuth()` (`media.ts:729`) while the v1 route has it — add it.
- **Verified:** `info.is_animated` passes through the send path unmodified
  (content bound verbatim, `src/api/rooms.ts:2513` → `:2534`; the only
  content check is the redaction `redacts` field) — only the
  storage/round-trip test remains.
- **Optional parity:** the v3 upload MIME whitelist is stricter than spec
  (403 for unlisted types, `media.ts:14-31`, `:190`) — decide keep-or-relax;
  the v1 `preview_url` route lacks v3's Browser Rendering branch
  (`:996` vs `:644-660`).
- **Optional feature:** animated GIF/WebP thumbnail passthrough for media
  with `info.is_animated` (MSC4230, v1.18).

### 15. Push rule ID semantics (v1.17 #2214)
- **Verified:** `PUT /pushrules` upserts — `INSERT ... ON CONFLICT
  (user_id, kind, rule_id) DO UPDATE` (`src/api/push.ts:784-787`), so a
  same-ID same-kind PUT overwrites (no duplicates) and cross-kind same IDs
  coexist by design (PK includes kind). Scope `global` and the `.m.rule.`
  default-prefix are guarded (`push.ts:729-736`).
- **Action:** tests only — double-PUT yields one updated row; cross-kind
  IDs coexist; `.m.rule.*` rejected.

### 15a. Threads pagination (unstable MSC3856, implemented here)
- **Code (verified):** `GET /v1/rooms/:roomId/threads` checks membership and
  caps `limit` at 100 but has no `from` parameter and returns only
  `{chunk}` — no `next_batch` (`src/api/relations.ts:233-292`), unlike the
  sibling relations endpoints which paginate with `limit+1` + token
  (`relations.ts:60`, `:110`).
- **Fix:** accept `from` (an origin_server_ts cursor), fetch `limit+1`,
  emit `next_batch` from the last row. **Test:** two-page walk of a room
  with more than `limit` threads.

### 15b. `/state` + `/state_ids`: required `event_id` vs permissive (decision)
- The v1.19 spec makes the singular `event_id` REQUIRED; the code treats it
  as optional and serves current state when absent (`federation.ts:1749`,
  `:1845`). The optional behavior is load-bearing: existing tests depend on
  it (`test/federation-state-at-event.test.ts:204-207`,
  `test/federation-api-routes.test.ts:1608-1615`) and the history-repair
  workflows use the unscoped form.
- **Decision:** keep permissive + document the deviation in the README, or
  make it required (400 M_MISSING_PARAM) after updating those tests and
  auditing internal callers first.

### 16. Conformance harness cadence
- Keep porting selected Complement/Sytest cases into the existing
  in-process mock-peer vitest harness (the one that reproduces Synapse
  receive-side auth rejections). Prioritize the areas touched above so each
  roadmap item lands with a spec-cited test.

### 17. Docs
- As items land: add MSC4287 / MSC4356 / MSC2545 / MSC4423 / MSC4268 rows to
  the README spec tables, record the v1 send_join/leave decision, and add a
  `CHANGELOG.md` entry per repo convention.

## Verified as conformant during this audit (do not re-litigate)

- Federation `/state` and `/state_ids`: the v1.19 spec parameter is the
  **singular, required `event_id`** (not `event_ids`); both handlers
  implement event-scoped state with the spec's 403-ACL / 404 semantics plus
  per-version wire-format mapping (`federation.ts:1747`, `1843`).
- Countersignature merge preservation (v1.19 clarifications #2341/#2385):
  `signJson` merges into the existing signatures object, never replacing
  other servers' keys (`src/utils/crypto.ts:294-301`); both the invite v2
  path (`federation.ts:3658-3663`) and policy-server countersigning
  (`src/services/policy-server.ts:113-118`) preserve the event-origin
  signature. Pin with a multi-signature survival test.
- `read_markers` writes `m.fully_read` + `m.read` + a real `m.read.private`
  receipt, and private receipts never federate (`src/api/receipts.ts:145-205`;
  the receipt endpoint accepts `m.read.private`, `receipts.ts:42`). Only a
  multi-signature/owner-visibility test is missing.
- New account-data types (`m.key_backup`, `m.recent_emoji`) take the plain
  D1 path and are served by both `/sync` and sliding sync (see items 6-7).
- MSC4268 relay paths are unrestricted end-to-end (to-device type binding,
  EDU relay in both directions, invitee device-key queries — see item 9).
- MSC4230 `info.is_animated` passes through the send path unmodified
  (see item 14).
- Push-rule PUT is an upsert on `(user_id, kind, rule_id)` — duplicate rows
  are impossible (`src/api/push.ts:784-787`).
- Media config field `m.upload.size` (dot form) matches the v1.19 spec text
  (`media.ts:731`, `:1077-1080`) — do NOT rename to `m.upload_size`.
- Appservice token direction is correct both ways (AS→HS requests use the
  as_token via `requireAppServiceAuth`; the HS→AS ping uses the hs_token)
  and the MSC2659 ping shapes match, including the absence of an
  `appservice_id` body field (`src/api/appservice.ts:13-26`, `:80-148`).
- `/messages` filter application is conformant
  (types/not_types/rooms/not_rooms/senders/not_senders/contains_url via
  `applyMessageEventFilter`, `rooms.ts:1661-1675`; `to` enforced as an
  exclusive bound, `:1719-1757`).
- POST /upload enforces the 50 MiB cap and returns the spec `{content_uri}`
  shape; all four MSC3916 authenticated media routes exist with the same
  semantics as the v3 routes (`media.ts:184-218`, `:858`, `:925`, `:996`,
